# Физическое разделение данных в мультитенантной системе (вариант C — гибрид)

Статус: **Реализовано** (фазы 1–5 для Postgres; открытые работы — см. «Открытые последующие работы»)
Основание: EU Cyber Resilience Act (Регламент (ЕС) 2024/2847), GDPR ст. 17/20/32 — см. [CRA_COMPLIANCE.md](../../CRA_COMPLIANCE.md)

## Целевая архитектура

Мультитенантная система переводится с чисто логического разделения (общие таблицы
со столбцами `TenantId` и фильтрацией запросов через `imtauth::ITenantFilterParam`)
на гибридную модель с физическим разделением:

- **Общий каталог (shared-каталог)**: кросс-тенантные таблицы остаются в центральной
  каталожной базе данных или в общей схеме:
  `Tenants`, `TenantMemberships`, `TenantInvitations`, `TenantRelationships`,
  `TenantConnection*`, `TenantPermissions`, `TenantEntityBindings`,
  `CrossTenantMessages`, `Contracts`, `CrossOrgGrants`, `OrderRequests`,
  `UserSessions`, а также новая реестровая таблица `TenantStorage`.
- **Данные тенантов**: все пользовательские данные, принадлежащие тенанту (документы,
  коллекции, роли, группы, настройки, предметные объекты), хранятся физически раздельно:
  - Стандарт: отдельная схема Postgres на тенанта (`tenant_<id>`), для SQLite —
    отдельный файл базы данных на тенанта.
  - Enterprise/резидентность данных: отдельная база данных на тенанта (через ту же
    абстракцию).
- **Defense in Depth**: Postgres Row-Level Security на оставшихся общих таблицах
  со столбцом `TenantId`.

### Запуск интеграционных тестов

Тест создаёт временную базу `imt_tenant_isolation_test` и временную роль без привилегий
(суперпользователь обходит RLS), после прогона удаляет обе. Пароль роли генерируется на
каждый запуск. Доступ администратора к серверу задаётся переменными окружения
`IMTCORE_TEST_PG_HOST` (по умолчанию `127.0.0.1`), `IMTCORE_TEST_PG_PORT` (`5432`),
`IMTCORE_TEST_PG_USER` (`postgres`) и `IMTCORE_TEST_PG_PASSWORD`. Без
`IMTCORE_TEST_PG_PASSWORD` все тесты пропускаются (`SKIP`), а не проходят.
В `PATH` должны быть `bin` Qt и `bin` PostgreSQL (`libpq.dll` для драйвера `QPSQL`).

| Интеграция с жизненным циклом тенанта | `Include/imtauth/CTenantManagerComp.{h,cpp}` | Опциональная ссылка `StorageProvisioner`: `CreateTenant` провижинит хранилище (при ошибке создание тенанта откатывается), `RemoveTenant` депровижинит |
| `imtdb::CTenantSchemaMigrationControllerComp` | `Include/imtdb/CTenantSchemaMigrationControllerComp.{h,cpp}` | Компонент (`ImtDatabasePck::TenantSchemaMigrationController`): реализация `IMigrationController`, выполняющая обёрнутый контроллер (`TenantMigrationController`) по одному разу для каждого тенанта с выделенной схемой (кроме `Archived`) — внутри контекста этого тенанта и со схемой тенанта в начале `search_path` |

Примечания:

- Провижининг **идемпотентен** — для уже зарегистрированного тенанта возвращается успех.
- При ошибке провижининга (tablespace, DDL, персистентность, регистрация) созданная
  им схема удаляется. Схема, существовавшая **до** провижининга, не удаляется никогда —
  её данные сохраняются.
- Для не-Postgres-бэкендов (например SQLite) провижинер регистрирует явное назначение
  на общую схему; выделенные файлы баз данных на тенанта появятся в более поздней фазе.
  Fail-closed-разрешение при этом остаётся неизменным.
- Назначения загружает при старте сам резолвер (ссылка `DatabaseEngine`). Это важно:
  компоненты ACF создаются лениво, и провижинер (его создаёт только `CTenantManagerComp`)
  мог бы быть ещё не создан к первому запросу — резолвер был бы пуст, и все тенантные
  делегаты получали бы отказ. `LoadTenantStorageAssignments()` провижинера остаётся для
  явной перезагрузки.

### Миграции схем тенантов

`CTenantSchemaMigrationControllerComp` подключается как `MigrationController` движка
(при необходимости вместе с миграциями общего каталога через
`CCompositeMigrationControllerComp`). Свойства:

- Список тенантов читается напрямую из таблицы `TenantStorage` (а не из резолвера): движок
  выполняет миграции в своём `OnComponentCreated`, когда резолвер может быть ещё не создан.
  Если задана ссылка `StorageResolver`, назначения регистрируются в нём, чтобы
  тенант-зависимые делегаты внутри обёрнутого контроллера (например
  `CObjectCollectionMigrationControllerComp`) разрешали схему тенанта.
- Неквалифицированные имена таблиц в SQL-скриптах миграций адресуют таблицы тенанта
  (`search_path`); после каждого тенанта `search_path` восстанавливается.
- Движок выполняет все миграции в **одной** транзакции: ошибка в схеме любого тенанта
  откатывает миграцию всех тенантов, и общая ревизия в `Revisions` остаётся согласованной.
  Цена — одна длинная транзакция при большом числе тенантов (см. нагрузочные тесты).
- `DdlScriptPaths` провижинера должны создавать таблицы в **текущей** версии схемы — так же,
  как скрипты `AutoCreateTable`: новый тенант сразу получает актуальную структуру, а
  последующие миграции применяются ко всем тенантам этим контроллером.
- Имена схем выводятся исключительно из санитизированных идентификаторов тенантов
  (`CTenantStorageRegistry::CreateSchemaName`) перед использованием в DDL-операторах
  (защита от SQL-инъекций; DDL не поддерживает привязку параметров).

### Семантика fail-closed

- Разрешение без зарегистрированного назначения завершается ошибкой (никакого тихого
  отката на общие данные). Только если `AllowSharedFallback` явно включён
  (переходный режим/миграция), разрешение выполняется на общую схему — компонент
  логирует это при старте как предупреждение.
- Пустые идентификаторы тенантов всегда отклоняются.
- Выделенные назначения (`OwnSchema`/`OwnDatabase`/`OwnFile`) без имени схемы и
  без ссылки на соединение отклоняются.

### Аудит-логирование (CRA, приложение I, часть I, 2(l))

`CTenantStorageResolverComp` логирует события, значимые для безопасности, через
инфраструктуру логирования (`ilog`):

- регистрация/обновление назначения хранилища (Info, с видом/схемой/соединением),
- удаление назначения (офбординг тенанта, Info),
- неудачные разрешения (предупреждение — потенциальное нарушение изоляции или
  ошибка конфигурации),
- включённый shared-fallback (предупреждение при старте компонента).

### Fail-closed в пути запроса

Если у SQL-делегата сконфигурирована ссылка `TenantStorageResolver`, `GetTableScheme()`
в следующих случаях возвращает sentinel-имя схемы `imt_tenant_storage_denied`
(запросы при этом завершаются ошибкой вместо случайного доступа к общим данным),
каждый раз с аудит-сообщением об ошибке:

- нет активного контекста тенанта (отсутствует `TenantId` в запросе),
- хранилище тенанта не разрешается (неизвестный тенант),
- статус хранилища не `Active` и не `Migrating` (например `Provisioning`, `Archived`).

Примечания:

- У делегатов со ссылкой `TenantStorageResolver` атрибут `AutoCreateTable` следует
  оставлять выключенным — выполнение DDL в схеме тенанта берёт на себя провижинер
  (фаза 2).
- Кросс-тенантные функции (общий каталог: тенанты, пользователи, лицензии) продолжают
  использовать делегаты **без** ссылки на резолвер и остаются без изменений.
- Row-Level Security на оставшихся общих таблицах остаётся второй линией обороны
  (см. модель угроз) и может быть дополнена на стороне БД.

### Делегаты документов

SQL делегатов строится через `GetTableSchemePrefix()` (на основе `GetTableScheme()`),
иначе разрешение схемы тенанта на него не действовало бы:

- `CSqlDatabaseDocumentDelegateCompBase` и `CSqlDatabaseObjectDelegateCompBase` раньше
  подставляли статический `TableSchema` напрямую: с резолвером документы тенанта читались
  и писались бы в общей схеме. Без резолвера поведение прежнее.
- `CSqlJsonDatabaseDelegateComp` (в том числе роли) исторически адресовал таблицу без
  схемы; схема тенанта добавляется только при заданном резолвере, без него запросы
  остаются неквалифицированными, как раньше.
- `CreateTenantBindingTableName()` намеренно остаётся на статической схеме:
  `TenantEntityBindings` — таблица общего каталога.
- `CSqlDatabaseDocumentDelegateLegacyComp` не адаптирован (в продуктах не используется)
  и не должен получать ссылку `TenantStorageResolver`.

### Файловые документы

`CSqlDatabaseFileDocumentDelegateComp` с резолвером хранит содержимое тенанта с выделенной
схемой в `<StorageRoot>/tenants/<схема>/` (`GetTenantStorePath()`): тенанты не делят и не
дедуплицируют содержимое между собой. Без разрешённого тенанта путь не выдаётся, документ
не пишется и не читается.

`CFileDocumentGarbageCollectorComp`:

- при обходе общего хранилища папка `tenants/` **никогда** не проверяется по общей
  таблице — иначе живые файлы тенантов считались бы мусором и удалялись;
- с ссылкой `TenantStorageResolver` каждый тенант с выделенной схемой получает отдельный
  проход: его папка против таблицы документов в его схеме;
- папки неизвестных тенантов только репортятся; если таблицу тенанта прочитать не
  удалось, его папка в этом проходе пропускается.

### Кросс-тенантные пути

Делегированный доступ (CrossOrgGrants, `IDelegatedAccess`) не читает данные чужой
организации из текущего контекста. Путь всегда такой:

1. Авторизация — по таблицам общего каталога (`TenantMemberships`, `CrossOrgGrants`) через
   делегаты **без** резолвера: `CGqlJwtSessionControllerComp::CanUseTenant` проверяет
   владение, членство или действующий грант.
2. Переключение — токен выдаётся с тенантом-целью; `IGqlContext::GetTenantId()` следующих
   запросов возвращает его, и `CGqlRequestHandlerCompBase` открывает его контекст.
3. Данные — читаются из хранилища тенанта-цели как обычные запросы этого тенанта.

Поэтому отдельного «моста» между схемами нет и не нужно: данные одного запроса всегда
принадлежат одному тенанту.

Ограничение для RLS: таблицы каталога по своей природе читаются через границы тенантов
(«все членства пользователя», «гранты, выданные моей организации»). Политика изоляции на
них молча сломала бы переключение тенантов и делегированный доступ.
`CTenantRlsControllerComp` отклоняет конфигурацию, в `TableNames` которой есть таблица
каталога (`CTenantRlsPolicyBuilder::IsCrossTenantCatalogTable()`), и не применяет в этом
случае ни одной политики. RLS предназначен для таблиц тенантов, оставшихся в общей схеме
(переходный режим, тенанты с `SharedSchema`).

## Миграция данных (фаза 4 — реализовано)

| Компонент | Расположение | Назначение |
|---|---|---|
| `imtdb::ITenantDataMigrator` | `Include/imtdb/ITenantDataMigrator.h` | Интерфейс: `MigrateTenantData`, `MigrateAllTenants` |
| `imtdb::CTenantDataMigrator` | `Include/imtdb/CTenantDataMigrator.{h,cpp}` | Основная логика: копирует строки тенанта (`INSERT INTO <tenantSchema>.T SELECT * FROM <sourceSchema>.T WHERE TenantId = :tenantId`), сверяет количество строк, идемпотентна; идентификаторы валидируются и заключаются в кавычки, значения передаются исключительно параметрами |
| `imtdb::CTenantDataMigratorComp` | `Include/imtdb/CTenantDataMigratorComp.{h,cpp}` | Компонент (`ImtDatabasePck::TenantDataMigrator`): разрешает целевую схему через резолвер, устанавливает статус хранилища `Migrating` (персистируется), мигрирует все сконфигурированные таблицы (`TableNames`), при успехе устанавливает `Active`; опционально `PurgeSourceRowsAfterMigration` и `VerifyChecksums` (только Postgres) |

Миграция каждого тенанта выполняется внутри его контекста (`CTenantContextScope`).
Без этого RLS на общих исходных таблицах скрывал бы все строки: мигратор скопировал бы
0 строк, «сверил» бы 0 = 0 и перевёл бы тенанта в `Active` с пустыми данными.

Верификация контрольными суммами (`VerifyChecksums`): для исходной и целевой таблицы
считается `md5` упорядоченного текстового представления строк тенанта. Она обнаруживает
расхождения содержимого при совпадающем числе строк, в том числе при идемпотентном
повторном запуске. На не-Postgres-бэкендах включённая верификация завершает миграцию
ошибкой (а не пропускается молча).

Ход выполнения по каждому тенанту:

1. Разрешение через резолвер — мигрируются только тенанты с выделенной схемой
   (`OwnSchema`) и статусом `Active`/`Migrating`.
2. Статус устанавливается в `Migrating` и персистируется — guard-механизмы фазы 3
   в этом состоянии по-прежнему разрешают доступ (переходный режим dual-read).
3. По каждой таблице: подсчёт исходных строк → копирование → подсчёт целевых строк →
   верификация. Уже полностью мигрированные таблицы пропускаются (идемпотентный
   повторный запуск); частичные копии приводят к ошибке с прерыванием (никакой
   тихой перезаписи).
4. При ошибке восстанавливается предыдущий статус; при успехе устанавливается статус
   `Active` и опционально удаляются исходные строки.

Файловые документы: таблицы из `FileDocumentTableNames` (подмножество `TableNames`)
после переноса строк получают и содержимое — файлы, на которые ссылаются дескрипторы
перенесённых строк, копируются из общего хранилища (`FileStorageRoot`) в хранилище
тенанта. Строка без валидного дескриптора или ссылка на отсутствующий файл завершают
миграцию ошибкой: иначе документ тенанта стал бы нечитаемым. Исходные файлы остаются
в общем хранилище; после очистки исходных строк их соберёт сборщик мусора.

Восстановление:

1. Архив проверяется **до** любых изменений: его оглавление (`pg_restore --list`) должно
   содержать схему именно этого тенанта. Без этой проверки `pg_restore --schema` на архиве
   другого тенанта не восстанавливает ничего с кодом 0 — схема была бы заменена пустой,
   данные тенанта уничтожены, а операция «успешна» (проверено тестом).
2. Тенант переводится в `Provisioning` — его запросы получают отказ (fail-closed).
3. Текущая схема переименовывается во временную `imt_restore_<uuid>`, создаётся пустая
   схема (`pg_restore --schema` саму схему не создаёт), выполняется
   `pg_restore --exit-on-error --single-transaction`.
4. При успехе временная схема удаляется; при ошибке частично восстановленная схема
   удаляется, прежняя возвращается на место. Если вернуть не удалось, тенант остаётся
   заблокированным, а прежние данные — во временной схеме для ручного восстановления.
5. Статус тенанта восстанавливается.

Пароль передаётся через `PGPASSWORD`, аргументы — списком (без интерпретации оболочкой).
Поддерживается только Postgres.

## Усиление защиты (фаза 5 — реализовано)

| Компонент | Расположение | Назначение |
|---|---|---|
| `imtdb::CTenantRlsPolicyBuilder` | `Include/imtdb/CTenantRlsPolicyBuilder.{h,cpp}` | Статическая генерация валидированных RLS-операторов (`ENABLE`/`FORCE ROW LEVEL SECURITY`, `DROP`/`CREATE POLICY`) и запросов `set_config` для сессионной переменной; идентификаторы валидируются и заключаются в кавычки, значение тенанта всегда передаётся параметром |
| `imtdb::ITenantRlsController` | `Include/imtdb/ITenantRlsController.h` | Интерфейс: `ApplyRowLevelSecurity` |
| `imtdb::CTenantRlsControllerComp` | `Include/imtdb/CTenantRlsControllerComp.{h,cpp}` | Компонент (`ImtDatabasePck::TenantRlsController`): применяет политики изоляции к сконфигурированным общим таблицам (`TableNames`, `TenantIdColumn`, `SessionVariableName`, по умолчанию `app.tenant_id`; опционально `ApplyOnStartup`); аудит-логирование; только Postgres (предупреждение на других бэкендах) |
| Привязка сессии | `Include/imtdb/CDatabaseEngineComp.{h,cpp}` | Атрибут движка `TenantSessionVariable`: синхронизирует сессионную переменную с контекстом тенанта потока перед каждым оператором (см. «Привязка сессии к тенанту») |
| Шифрованные табличные пространства | `Include/imtdb/CTenantStorageProvisionerComp.{h,cpp}` | Новый атрибут `DefaultTablespace`: перед выполнением DDL устанавливается `SET default_tablespace` (после — сбрасывается через `RESET`), чтобы таблицы тенанта размещались на шифрованном томе/табличном пространстве |

### Принцип работы RLS-политик

- Политика на таблицу: `USING ("TenantId"::text = current_setting('app.tenant_id', true))`.
- `current_setting(..., true)` возвращает `NULL`, если переменная не установлена —
  сессии без привязанного тенанта не видят **ни одной** строки (fail-closed).
- `FORCE ROW LEVEL SECURITY` применяет политику также к владельцу таблицы.
- Повторное применение идемпотентно (`DROP POLICY IF EXISTS` перед `CREATE POLICY`).

### Привязка сессии к тенанту

Переменную `app.tenant_id` выставляет движок `CDatabaseEngineComp` (атрибут
`TenantSessionVariable`, по умолчанию пуст — привязка выключена). Соединения движка
живут по одному на поток и обслуживают запросы разных тенантов по очереди, поэтому
привязка синхронизируется перед **каждым** оператором и перед началом транзакции:

- значение берётся из контекста потока (`CTenantContextScope`) и передаётся
  параметром через `set_config` — никакой конкатенации значений тенанта;
- без контекста переменная сбрасывается в пустую строку — следующий запрос на том же
  потоке не видит строк предыдущего тенанта (fail-closed);
- последнее привязанное значение кэшируется на соединение; кэш сбрасывается при
  откате транзакции (откат возвращает и `set_config`), переподключении и завершении
  потока;
- если привязка не удалась, оператор не выполняется;
- поддерживается только Postgres; некорректное имя переменной выключает привязку с
  критическим сообщением — политики тогда не видят тенанта и не пропускают строк.

Отдельного API привязки нет намеренно: ручной `set_config` в обход движка
рассинхронизировал бы кэш, и следующий запрос другого тенанта на том же потоке
выполнился бы с чужим значением. Код без контекста тенанта (фоновые потоки,
обработчики вне GraphQL) не видит строк защищённых таблиц, пока не откроет
`CTenantContextScope` явно. Миграции, изменяющие защищённые таблицы, должны
выполняться ролью с `BYPASSRLS` или внутри контекста тенанта.

### Шифрование на тенанта

- **Postgres**: указать в `DefaultTablespace` провижинера табличное пространство,
  расположенное на шифрованном томе (LUKS/dm-crypt, шифрование EBS и т. п.) —
  прозрачно для кода приложения.
- **SQLite** (выделенные файлы тенантов): шифрованные контейнеры или
  SQLCipher-совместимые бэкенды; размещение в `<root>/tenants/<tenantId>/`.

### Открытые последующие работы

- **Нагрузочные тесты** с большим числом схем (размер каталога, число соединений,
  длительность единой транзакции миграции) перед enterprise-развёртыванием.
- **SQLite — осознанно без физического разделения.** SQLite используется для
  локальных/однотенантных установок без сервера БД и для тестов (в продуктах — только
  Puma `PumaServerSl`). Провижинер регистрирует для SQLite общую схему, изоляция
  остаётся логической (`TenantId`). Отдельный файл на тенанта потребовал бы `ATTACH` на
  соединение потока (лимит 10 баз, переключение невозможно внутри транзакции и при
  открытых запросах) в общем для всех движке — риск не оправдан для этих сценариев.
- **Подключение в продуктах**: ни один `.acc` ещё не ссылается на эти компоненты —
  без конфигурации поведение прежнее (логическое разделение по `TenantId`).

## Фазы реализации

1. **Фундамент (реализовано)** — интерфейс резолвера, реестр, компонент,
   реестровая таблица, тесты, документация.
2. **Провижининг и жизненный цикл (реализовано)** — при создании тенанта создаётся
   схема и выполняются существующие DDL-скрипты с `${TableScheme}`; персистентность
   реестра через таблицу `TenantStorage` с загрузкой резолвером при старте; откат
   создания тенанта и созданной схемы при ошибках провижининга; миграции по всем
   схемам тенантов (`CTenantSchemaMigrationControllerComp`); бэкап и восстановление
   на тенанта (`CTenantStorageBackupComp`).
3. **Защита пути запроса (реализовано)** — `GetTableScheme()` динамически через
   потоколокальный контекст тенанта (`imtbase::CTenantContextScope`, устанавливается
   из `IGqlContext` в `CGqlRequestHandlerCompBase`) + резолвер; fail-closed-guard
   (отсутствующий/неизвестный TenantId → sentinel-схема, запрос завершается ошибкой).
   Кросс-тенантные пути (CrossOrgGrants, DelegatedAccess): авторизация по общему
   каталогу и переключение контекста на тенант-цель; RLS на таблицах каталога запрещён.
4. **Миграция данных (реализовано)** — `CTenantDataMigratorComp` копирует по каждому
   тенанту строки из общих таблиц в схему тенанта внутри контекста тенанта, сверяет
   количество строк и (опционально) контрольные суммы, переключает статус
   `Migrating` → `Active`; идемпотентные повторные запуски; опциональная очистка
   исходных строк; копирование содержимого файловых документов в хранилище тенанта.
5. **Усиление защиты (реализовано)** — Row-Level Security на общих таблицах через
   `CTenantRlsControllerComp`; привязка `app.tenant_id` к контексту потока в движке
   перед каждым оператором (fail-closed); шифрованные табличные пространства через
   `DefaultTablespace` провижинера. Открыто: нагрузочные тесты с большим числом схем.

## Модель угроз (остаточные риски)

- **Общий каталог** остаётся общей поверхностью атаки: доступ только через делегаты
  с фильтром `TenantId`; RLS как вторая линия обороны (фаза 3); минимальные права
  пользователя БД.
- **Ошибка конфигурации `AllowSharedFallback`**: включение отключает
  fail-closed-защиту; поэтому при старте фиксируется в аудите как предупреждение и
  предназначено только для переходного режима миграции.
- **Коллизии имён схем**: `CreateSchemaNameForTenant` санитизирует идентификаторы;
  при коллизии после санитизации провижининг (фаза 2) должен обеспечивать уникальные
  имена (например, UUID-идентификаторы тенантов).
- **Время выполнения миграции** масштабируется с числом тенантов; миграции должны
  быть идемпотентными и возобновляемыми по каждому тенанту.
