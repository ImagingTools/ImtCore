# Один контроллер на документ, ветки и обновление по changeSet

Это проект, код по нему не написан. Имена новых типов, функций и полей условные.

Метка правки `changeId`, на которую опирается проект, делается отдельно и ещё не влита.

## Задача

Сейчас у каждого view документа свой контроллер и своя модель. Отсюда три проблемы:

- клиент перечитывает репрезентацию, даже если изменение её не касается;
- view B не может взять данные view A: ему нужен свой запрос, хотя данные уже могли быть получены;
- логика чтения и записи разнесена по `DocumentDecorator` и контроллерам каждого типа.

## Решение

У документа один контроллер и одна репрезентация, разделённая на ветки. Каждый view работает с нужными ему ветками.

```
Документ
  └─ DocumentRepresentationController   один на документ, общий тип для всех документов
       ├─ ветка "licenses"   ← view Licenses
       └─ ветка "device"     ← view Licenses, view General
```

| Кто | За что отвечает |
|---|---|
| Контроллер | Порядок запросов, `changeId`, свежесть веток, обновление view, ожидание для `Save`, `Undo`, `Redo` |
| Ветка | Своя часть модели, команда записи, правило `isAffectedBy` |
| View | `updateGui`, `updateModel`, список нужных веток |

Подклассы контроллера на каждый тип больше не нужны: автор объявляет только ветки.

## Пример

Документ `Device` с двумя экранами. Для экрана лицензий нужны `licenses` и `device`, для основного экрана только `device`.

### Регистрация

```qml
registerDocumentType("Device", qsTr("Device"))
setDocumentRepresentation("Device", DeviceCommandIds.s_getDeviceDocumentRepresentation, deviceRepresentationComp)

addDocumentBranch("Device", licensesBranchComp)
addDocumentBranch("Device", deviceBranchComp)

addDocumentView("Device", "Licenses", licensesEditorComp, ["licenses", "device"])
addDocumentView("Device", "General", generalEditorComp, ["device"])
```

Первая ветка в списке становится `model` экрана. Остальные загружаются вместе с ним.

### Ветка

```qml
Component {
	id: licensesBranchComp

	DocumentRepresentationBranch {
		id: licensesBranch

		branchId: "licenses"
		writeCommandId: DeviceCommandIds.s_updateLicensesFromRepresentation

		property UpdateLicensesInput updateInput: UpdateLicensesInput {}

		function createWriteInput(){
			licensesBranch.updateInput.m_documentId = licensesBranch.documentId
			licensesBranch.updateInput.m_licenses = licensesBranch.model
			return licensesBranch.updateInput
		}
	}
}
```

### Экран

```qml
DocumentViewBase {
	id: licensesEditor

	function updateGui(){
		let device = licensesEditor.representation.branch("device")
		deviceNameLabel.text = device.model.m_name
		countInput.text = licensesEditor.model.m_count
	}

	function updateModel(){
		licensesEditor.model.m_count = countInput.text
	}
}
```

## Чтение: один запрос с выбором веток

Команда чтения одна на документ, а ветки — это её поля. Запрашиваются только устаревшие ветки, нужные видимому экрану:

```graphql
query {
	GetDeviceDocumentRepresentation(input: {id: "..."}) {
		licenses
		device
	}
}
```

В SDL ветки должны быть необязательными:

```
type DeviceDocumentRepresentation {
	licenses: DeviceLicensesData
	device: DeviceData
}
```

Обработчик на сервере строит только запрошенное:

```cpp
const auto requestInfo = gqlRequest.GetRequestInfo();

if (requestInfo.isLicensesRequested){
	response.licenses = BuildLicenses(*devicePtr);
}

if (requestInfo.isDeviceRequested){
	response.device = BuildDevice(*devicePtr);
}
```

| Действие | Запрашиваемые ветки | Запросы |
|---|---|---|
| Открыть `Licenses` | `licenses`, `device` | 1 |
| Открыть `General` | Ничего, ветка уже есть | 0 |
| Вернуться на `Licenses` | Ничего | 0 |
| Устарела только `device`, открыт `Licenses` | `device` | 1 |
| Undo, открыт `General` | `device`; `licenses` дождётся показа своего экрана | 1 |

Документу с одной веткой отдельная команда не нужна: ветка читается своей нынешней командой `Get...Representation`.

## Запись: по одной ветке

Записи идут по веткам и по одной на документ. Полная запись одной ветки не может затереть другую, незагруженную.

Порядок запросов:

1. Запись не ждёт чтения.
2. Чтение ждёт все записи, поэтому видит свою правку.
3. На документ идёт одно чтение за раз.
4. `Save`, `Undo` и `Redo` ждут записи. Отказ записи их отменяет.

Если во время чтения появилась правка, ответ отбрасывается только для этой ветки: она прочитается после записи.

## Что приходит при изменении

В уведомлении `DocumentChanged` появляются сведения об изменении:

| Поле | Смысл | Пример |
|---|---|---|
| `changeId` | Метка правки: по ней клиент узнаёт свою правку | `3f2a…` |
| `changeSet` | Какие поля изменились, без значений | `licenses.count` |
| `changeSource` | Серверная служба, которая сделала изменение | `TicketService` |

Пути начинаются с имени ветки, поэтому у всех веток они общие. Для правки клиента `changeSource` не нужен.

Главное правило: **об изменении сообщает тот, кто знает, что изменилось. Если не знает никто, все перечитывают.**

| Кто меняет | Кто сообщает `changeSet` |
|---|---|
| Пользователь правит ветку | Клиент: он знает, какие поля изменил |
| Сервер сам или по команде клиента | Обработчик на сервере, если он это объявил |
| Undo, откаты, изменения без объявления | Никто: все перечитывают |

## Как ветка решает, обновляться ли

```qml
function isAffectedBy(changeSet, isOwnEdit, changeSource){
	return !isOwnEdit
}
```

`isOwnEdit` означает, что это правка именно этой ветки из этой сессии, и результат уже есть в модели.
По умолчанию своя правка не вызывает чтения, а любое другое изменение делает ветку устаревшей.

| Что пришло | Решение |
|---|---|
| Своя метка | Вызвать правило, по умолчанию не обновляться |
| Есть `changeSet` или `changeSource` | Вызвать правило, по умолчанию обновиться |
| Нет сведений | Обновиться, правило не вызывается |

Устаревшая ветка читается, только если она нужна видимому экрану. Иначе она дождётся показа.

### Примеры правил

Смена названия устройства не влияет на лицензии:

```qml
function isAffectedBy(changeSet, isOwnEdit, changeSource){
	if (ChangeSetHelper.isOnlyWithin(changeSet, "device.name")){
		return false
	}

	return !isOwnEdit
}
```

После своей правки нужны данные с сервера, потому что он пересчитывает права при смене родительских ролей:

```qml
function isAffectedBy(changeSet, isOwnEdit, changeSource){
	if (isOwnEdit){
		return ChangeSetHelper.isAffected(changeSet, "role.parentRoles")
	}

	return true
}
```

## Изменения без changeSet на клиенте

| Случай | Пример | Придёт ли `DocumentChanged` |
|---|---|---|
| Сервер сам меняет документ | После сохранения заявка получает номер; откат записи | Да |
| Клиент шлёт команду, документ меняет сервер | Клиент не правит модель, а обновляется после запроса | Да, если обработчик меняет документ через `SetDocumentData` |
| Данные лежат вне документа | Участники и приглашения организации | Нет |

**Сервер сам меняет документ.** Без дополнительной работы всё безопасно: сведений нет, поэтому все ветки устаревают.
Если лишние чтения мешают, обработчик объявляет, что изменил:

```cpp
imtdoc::DocumentChangeInfo changeInfo;
changeInfo.source = "TicketService";
changeInfo.changeSet = {"ticket.number", "ticket.id", "ticket.conversationId"};
m_documentManagerCompPtr->SetDocumentData(userId, documentId, *documentPtr, changeInfo);
```

**Клиент шлёт команду.** Команду нельзя считать своей правкой: её результата в модели нет, и без чтения на экране останутся старые данные.
Поэтому команда не отмечается как `isOwnEdit`, и ветка по умолчанию обновляется. Клиент не угадывает `changeSet`: при необходимости
его объявляет обработчик. Ручное чтение после команды убирается, иначе будет два запроса.

**Данные вне документа.** Уведомления нет, поэтому нужно явное чтение ветки: `representation.reload("tenant")`.
Сигналом служит свой канал уведомлений или ответ команды.

## Если ветка недоступна

Обработчик не роняет весь запрос из-за одной ветки: он её не заполняет. Запрошенная, но не пришедшая ветка получает состояние «недоступна».

| Ветка экрана | Что происходит |
|---|---|
| Обязательная | Ошибка всего экрана |
| Необязательная | Экран показывается, работая без этой ветки |

Необязательные ветки объявляет сам экран:

```qml
DocumentViewBase {
	optionalBranchIds: ["device"]
}
```

Экран показывается, когда готовы все его обязательные ветки. Незагруженную ветку записывать нельзя.

## Правила для авторов

1. Ответ `false` в `isAffectedBy` — это обещание, что изменение точно не меняет данные ветки. Сюда входят и значения, которые сервер вычисляет при чтении.
2. Пишите правило, только если лишний запрос заметно мешает.
3. Записывайте пути как ключи SDL с именем ветки: `device.settings`, а не `m_settings`.
4. На каждое правило нужен тест с настоящим изменением: при переименовании поля правило сломается молча.
5. Что должно меняться вместе, держите в одной ветке: правка двух веток — это две записи и два шага undo.
6. Обработчик на сервере объявляет только то, что изменил точно. Если не уверены, не объявляйте `changeSet`.
7. Ветки в составном типе SDL только необязательные. Не используйте имена членов `CItemModelBase`, например `finished`.

## Проблемы и решения

| Проблема | Решение |
|---|---|
| Команда одна, а права на ветки могут быть разными: возможна утечка данных | Обработчик проверяет права по каждой запрошенной ветке; на каждую ветку нужен тест отказа |
| Обновление второй ветки затирает текст, который ещё печатают | `onBranchUpdated(branchId)`: по умолчанию полный `doUpdateGui`, но экран может обновить только свою часть |
| Изменение пришло, пока идёт чтение | Ветка перестаёт быть устаревшей при отправке запроса, поэтому новое уведомление снова её пометит |
| Тяжёлая ветка задерживает лёгкую | Начать с одного чтения и замерить; параллельные запросы для разных веток добавить при необходимости |
| Обработчик игнорирует выбор полей и считает всё | Проверять флаги в каждом обработчике и замерить тяжёлые типы |
| Продукт не может добавить поле в тип SDL из ImtCore | Ветка со своей командой чтения как исключение |
| Запись ветки целиком возвращает старое значение поля, которое изменил сервер или другая сессия | Проблема есть и сейчас; это отдельная задача |
| Данные от клиента в `changeSet` могут уйти другим пользователям | Сервер проверяет размер и формат. Некорректные данные отбрасываются, правка применяется. Значения полей не передаются никогда |
| Слишком большой `changeSet` | Клиент его не отправляет, и остальные ветки обновляются |

## Порядок работ

1. **`changeId`.** Влить метку правки: это убирает лишние чтения после своих правок.
2. **Один контроллер на документ.** Каждый старый контроллер становится одной веткой, поведение не меняется, `DocumentDecorator` уходит.
3. **`isAffectedBy` и `changeSet`.** Сначала только на клиенте. Пересылка через сервер и объявления в обработчиках — только если важно убрать лишние запросы в других сессиях и после серверных изменений.
4. **Составное чтение и общение веток.** Делать на первом настоящем документе с несколькими view: сейчас в продуктах у каждого типа один view, а проверять эту часть на демо мало.

Каждый этап проверяется в Qt и JQML.

## Что нужно проверить

- Как сервер отвечает на запрос ветки без подполей. По сгенерированному коду вся ветка должна вернуться, но вживую это не запускалось.
- Как выбор веток проходит при пересылке запроса с одного сервера на другой.
- Как сравнение путей работает с записями, в которых есть только путь и операция.
- Какой размер заголовка с `changeSet` проходит через все прокси и веб-сервер.
