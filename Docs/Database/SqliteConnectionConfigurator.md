# Настройка соединений SQLite: `IDatabaseConnectionConfigurator` и `CSqliteConnectionConfiguratorComp`

## Зачем

`CDatabaseEngineComp` открывает по одному соединению на поток и не меняет настройки драйвера Qt. У драйвера `QSQLITE` по умолчанию
(проверено на Qt 6.8.3 и 6.11.1):

| Параметр | По умолчанию |
|---|---|
| `journal_mode` | `delete` |
| `foreign_keys` | `0` (ссылки `REFERENCES` не проверяются) |
| `synchronous` | `FULL` |
| `busy_timeout` | 5000 мс |

Следствия для сервера, где базу читают и пишут разные потоки:

- Пока один поток не закончил запрос (длинный список, сверка), запись из другого потока ждёт `busy_timeout` и падает с «database is locked».
- Запись, ссылающаяся на несуществующую запись, принимается без ошибки.

## Как устроено

Общий движок ничего не знает о конкретной базе. Он зависит от интерфейса:

```cpp
class IDatabaseConnectionConfigurator: virtual public istd::IPolymorphic
{
public:
	virtual bool ConfigureConnection(QSqlDatabase& databaseConnection, QString& errorMessage) const = 0;
};
```

- У `CDatabaseEngineComp` есть необязательная ссылка `ConnectionConfigurator`. Если она задана, движок вызывает конфигуратор для
  каждого открытого соединения (соединение на поток, при каждом открытии). Метод вызывается из разных потоков одновременно и не должен
  менять состояние конфигуратора.
- Результат важен: `true` — соединение настроено так, как нужно конфигуратору; `false` и причина в `errorMessage` — в случае неудачной настройки.
- Без ссылки ничего не вызывается: все приложения и композиции, которые используют `CDatabaseEngineComp`, работают
  как раньше. Движок не менялся, кроме этой ссылки.
- Конфигураторы — отдельные компоненты, их можно добавлять, не трогая движок.

## `SqliteConnectionConfigurator`

Компонент `SqliteConnectionConfigurator` пакета `ImtDatabasePck` (`imtdb::CSqliteConnectionConfiguratorComp`) настраивает соединение
SQLite для параллельной работы. Все настройки — атрибуты, значения по умолчанию подходят для сервера:

| Атрибут | Тип | По умолчанию | Допустимые значения |
|---|---|---|---|
| `JournalMode` | число (перечисление `JournalMode`) | `4` (WAL) | `0` DELETE (умолчание драйвера), `1` TRUNCATE, `2` PERSIST, `3` MEMORY, `4` WAL, `5` OFF |
| `Synchronous` | число (перечисление `Synchronous`) | `1` (NORMAL) | `0` OFF, `1` NORMAL, `2` FULL (умолчание драйвера), `3` EXTRA |
| `ForeignKeys` | логический | `true` | проверять ли ссылки между таблицами |
| `BusyTimeoutMs` | целое | `5000` | время ожидания блокировки другого соединения, мс; `0` — не ждать |

Перечисления описаны в классе конфигуратора (`I_DECLARE_ENUM`), число атрибута — значение перечисления; название режима для `PRAGMA`
берётся из перечисления, а не сравнением строк. Значение, которого нет в перечислении, и отрицательный `BusyTimeoutMs` один раз при
создании компонента попадают в журнал как ошибка. Недопустимые атрибуты — это ошибка всего конфигуратора: пока хотя бы один из них
недопустим, ни один `PRAGMA` не выполняется, и каждое соединение считается не настроенным (см. «Обработку ошибок»).

После открытия каждого соединения выполняются `PRAGMA busy_timeout` (первым: переключение режима журнала берёт блокировку),
`journal_mode`, `synchronous`, `foreign_keys`.

## Обработка ошибок

Соединение, которое считают настроенным, но которое не настроено (например, без WAL), делает базу медленной или заблокированной без
всякого признака причины. Поэтому результат проверяется, а не предполагается:

- **Каждая настройка читается обратно.** SQLite не сообщает об ошибке, если не может применить настройку: `journal_mode=WAL` в базе
  в памяти или на сетевой файловой системе тихо оставляет прежний режим. Конфигуратор после каждого `PRAGMA ...=значение` выполняет
  `PRAGMA ...` и сравнивает прочитанное с ожидаемым («journal_mode is 'memory' instead of 'wal'»).
- **Конфигуратор возвращает `false` с причиной**, если настройка не применилась, значение атрибута недопустимо (значение вне
  перечисления, отрицательный `BusyTimeoutMs`; один раз при создании компонента это пишется в журнал) или драйвер соединения не `QSQLITE`.
  Если недопустимы атрибуты или драйвер, ни один `PRAGMA` не выполняется. Если не применилась настройка, остальные всё равно
  выполняются, и в причину попадают все проблемы сразу.
- **Движок не использует такое соединение.** Он пишет причину в свой журнал (`The connection to the database '...' is not set up and is
  not used: ...`), **удаляет** соединение (а не только закрывает: Qt открывает закрытое соединение заново, когда его запрашивают по
  имени, и движок продолжил бы работать с ненастроенным соединением) и считает базу недоступной. Каждый вызов движка возвращает ошибку
  соединения (`QSqlError::ConnectionError`), а не пустой результат без ошибки; при следующем обращении настройка выполняется заново.
- **Для SQLite движок больше не проверяет «сервер».** Раньше при неудачном открытии любой базы движок вёл себя как при недоступном
  PostgreSQL: «подключался» драйвером SQLite к базе с именем `MaintainanceDatabase` (по умолчанию `postgres`) в текущем каталоге, что
  создавало лишний файл. SQLite — это файл, сервера нет: теперь при неудаче открытия пишется ошибка и возвращается `false`.

Значения WAL и `synchronous` дают: читатели и писатель не блокируют друг друга; с WAL меньше `fsync`, при потере питания можно
потерять последние коммиты, но не повредить базу.

## Как подключить

В композиции у движка (`SqlDatabaseEngine`, `DbType = QSQLITE`) ссылка `ConnectionConfigurator` указывает на компонент
`SqliteConnectionConfigurator`; значения атрибутов задаются в композиции (или экспортируются и задаются приложением).

## Что нужно знать

- Режим журнала хранится в файле базы: файл, переведённый в WAL, остаётся в WAL, пока кто-нибудь явно не выполнит
  `PRAGMA journal_mode=DELETE`. Рядом с базой появляются файлы `-wal` и `-shm`.
- Копировать базу в режиме WAL одним файлом `.db` нельзя (потеряются последние записи): нужен API резервной копии SQLite или
  копирование вместе с `-wal`.
- `foreign_keys` и `synchronous` действуют на соединение, а не на файл; поэтому настройка применяется к каждому соединению.

## Проверка

`imtdbTest` (`CDatabaseEngineSqliteTest`) работает на композиции `Include/imtdb/Test/Partitura/DatabaseEnginesTest.acc`: класс
композиции создаёт ARXC (настройка в `Include/imtdb/Test/CMake/CMakeLists.txt`), пути баз и значения атрибутов конфигуратора — экспортируемые
атрибуты композиции. В композиции три движка: обычный, со ссылкой на конфигуратор и со ссылкой на конфигуратор для базы в памяти,
где WAL включить нельзя; конфигуратор экспортирован для прямых проверок. 20 проверок:

- обычный движок не меняет настройки драйвера;
- атрибуты по умолчанию дают WAL, NORMAL, ссылки проверяются, ожидание 5000 мс;
- каждое значение перечислений `JournalMode` и `Synchronous`, `ForeignKeys`, `BusyTimeoutMs` доходят до `PRAGMA`;
- конфигуратор сообщает об успехе (`true`, причина пуста) и о неудаче (`false` и причина): значения вне перечислений и отрицательное
  ожидание, настройка, которую SQLite молча не применил (WAL в базе в памяти); остальные настройки при этом применяются;
- движок не использует соединение, которое не настроено: каждый вызов (и на соединении другого потока) возвращает ошибку соединения,
  транзакция не начинается; проверено на отказ — если соединение только закрывать, а не удалять, оба теста падают;
- настройка применяется на соединении другого потока;
- ссылка на несуществующую запись: у обычного движка принимается, с конфигуратором отклоняется, при `ForeignKeys=false` принимается;
- запись из другого потока при незавершённом чтении проходит сразу с конфигуратором (WAL) и падает с «database is locked» у обычного движка.
