# Контракты организаций — модель и план

Статус: проект, 2026-11-23. Заменяет `imtauth::IContract`, самостоятельную Relationship и её Proposal.

## Изоляция по продукту

Контракт принадлежит ровно одному продукту. `ProductId` берётся из контекста запроса при создании, сериализуется и копируется вместе с контрактом, но не входит в хэш условий и не меняется при редактировании. В другом продукте контракт недоступен: чтение, журнал, вложения, личные данные, команды, выдача прав, связанные организации и делегированный вход работают только в продукте контракта. Отказ не раскрывает существование чужого контракта.

Выдача прав не имеет собственного `productId`: каждое право должно входить в опубликованное дерево продукта контракта и в область прав дарителя. Для самой Puma используется её дерево прав. Рамочный и заменяемый контракты должны принадлежать тому же продукту. Справочники ролей сторон и типов остаются общими, нумерация остаётся общей для организации.

Суперпользователь в Puma может читать контракты всех продуктов с указанием продукта. Чужой контракт помечается `isReadOnly`; команды по нему запрещены и на сервере. Исключение администратора не распространяется на делегированный доступ и обмен документами.

Уведомления, напоминания и `OnContractNotification` относятся к продукту контракта. `OnContractsChanged` содержит `productId` и направляется только серверу соответствующего продукта. Старые контракты без продукта очищаются на тестовом стенде; миграция с угадыванием продукта не предусмотрена.

## 1. Что есть сейчас

| Сущность | Что моделирует | Кто использует |
|---|---|---|
| Connection code | секретный код организации, передаётся вне системы; можно отключить | запрос на подключение |
| Connection request → Connection | A ввела код B, B одобрила: организации знают друг друга | Relationship, Proposal |
| Relationship + Proposal | роль пары (A — поставщик B), срок, scope; обе стороны одобряют предложение | брокер сообщений (`ValidateRelationship`), расшарки (`CDocumentShareManagerComp`: нужна действующая связь, расшарки заканчиваются вместе с ней), `ITenantRelationshipProvider` (список партнёров, `relatedSince`) |
| CrossOrgGrant | A отдаёт B свои роли; действует на всех участников B | `IDelegatedAccess`, вход в организацию, профиль |
| DocumentShare | документ A доступен B с уровнем доступа и группами B | коллекции документов |
| CrossTenantMessage / OrderRequest | обмен данными | брокер, домены |
| Contract | две стороны, одна Relationship, текст `terms` | только GQL CRUD, ни на что не влияет |

## 2. Нужна ли Relationship

**Relationship — это двусторонний контракт без документа.** У неё есть стороны, роли, срок, scope, двустороннее одобрение (Proposal = подписание), статусы. Контракт в той же системе — то же самое для N сторон плюс условия, вложения и права. Держать обе сущности — значит иметь два процесса согласования, два справочника ролей, два понятия срока и вечный вопрос «что главнее, если связь архивирована, а контракт действует».

**Решение: самостоятельной Relationship нет. Контракт — это стороны и набор связей между ними; связь существует, пока действует контракт.**

```
Connection     — адресная книга: кто может присылать мне приглашения напрямую. Доступа не даёт.
Contract       — согласие + условия; единственный источник доверия и доступа.
  ├─ Party     — сторона: роль в контракте, состояние, подписанты
  ├─ Link      — связь пары сторон (бывшая Relationship): направленные роли пары
  │    ├─ Allocation   — права одной стороны связи другой
  │    │    └─ Distribution — получатель раздаёт права своим группам
  │    └─ основание для сообщений и расшарок между этой парой
  └─ Reference / Attachment / Event
ITenantRelationshipProvider — вычисляемое представление: пары, связанные действующими контрактами.
```

### 2.1 Почему контракт — это набор связей, а не набор Relationship

Контракт действительно состоит из парных связей, но они **принадлежат контракту**, а не живут отдельно:

- **Подписываются вместе.** Сторона, подписывая контракт, видит всех участников и все связи и соглашается со всем сразу. Отдельные Relationship пришлось бы одобрять по одной, и контракт мог бы оказаться наполовину подтверждённым.
- **Живут и заканчиваются вместе.** Расторжение, замена (`SUPERSEDES`), выход стороны или истечение срока закрывают связи в той же транзакции. Отдельная связь, переживающая контракт, — та самая рассинхронизация, от которой уходим.
- **Неизменяемы после активации**, как и весь контракт.

### 2.2 Связь (`ContractLink`)

| Поле | Смысл |
|---|---|
| `linkId` | стабильный id внутри контракта |
| стороны A и B | две стороны этого контракта |
| роль A к B, роль B к A | id из справочника ролей + снимок названия; по умолчанию — роли сторон в контракте и парная роль |
| срок | необязателен, внутри срока контракта |
| что разрешено | обмен сообщениями (типы), расшарки документов — по умолчанию оба |
| распределения | права A → B и B → A (раздел 3.7) |

Правила:

- Каждая сторона входит хотя бы в одну связь.
- Роли задаются **на связи**: генподрядчик — исполнитель для заказчика и заказчик для субподрядчика.
- Двусторонний контракт получает одну связь автоматически. Для N сторон связи задаёт инициатор, тип контракта подсказывает схему (звезда вокруг заказчика, полная сетка для NDA).
- Связь **действует** = контракт действует ∧ ни одна из двух сторон не вышла ∧ сейчас внутри срока связи.
- Если пару связывают несколько контрактов, представление объединяет их: пара связана, пока действует хотя бы одна связь. `relatedSince` считается по периодам всех связей пары (`GetUninterruptedStart` уже это умеет).

### 2.3 Что меняется у потребителей

| Потребитель | Было | Будет |
|---|---|---|
| `ITenantRelationshipProvider` | читает `TenantRelationships` | тот же интерфейс, реализация по действующим связям контрактов; `CDocumentShareManagerComp` и список партнёров не меняются |
| Брокер сообщений | `relationshipId`, проверка Relationship | `contractId` + `linkId` обязательны; связь действует, тип сообщения разрешён связью |
| `CrossTenantMessage`, `OrderRequest` | `relationshipId` | `contractId`, `linkId` |
| DocumentShare | нужна действующая Relationship | нужна действующая связь пары; необязательный `contractId` закрепляет расшарку за конкретным контрактом |
| Запрос на подключение | может нести предложение Relationship | может нести черновик простого контракта (4.2, тип «Сотрудничество»); одобрение запроса = подпись |

### 2.4 Простой случай остаётся простым

Нынешнее «подключиться и стать партнёрами» — это контракт системного типа **«Сотрудничество»**: две стороны, одна связь, роли, срок, подтверждение в системе, без вложений и с одной подписью от стороны. Для пользователя это один шаг, как сейчас Proposal. Документы, права и N сторон появляются, только когда они нужны.

## 3. Контракт

Документ общего пространства: не принадлежит одной организации, видят его только стороны. **Все стороны видят весь общий текст**, включая всех участников, все связи и распределения прав. Подписывают они условия, связи и стороны; распределение прав — решение каждой стороны о своих правах, в подпись не входит (3.7). Условия, которые должны остаться между двумя сторонами, оформляются дочерним контрактом (`FRAMEWORK`) этих двоих.

### 3.1 Общие условия (входят в подпись)

| Поле | Смысл |
|---|---|
| id, номер | номер — по счётчику инициатора (`<префикс>-<год>-<n>`) |
| название, описание, `terms` | предмет и текст условий |
| тип | элемент справочника типов (4.2) |
| инициатор | организация, создавшая контракт; только она правит черновик |
| стороны, связи | 3.3, 2.2 |
| срок | `effectiveFrom` (дата или «с последней подписи»), `term` или `validUntil` |
| продление | `autoRenew`, `renewalPeriod`, `renewalNoticePeriod` |
| выход | `terminationNoticePeriod` |
| сумма | `value` + `currency`, необязательно |
| ссылки, вложения | 3.5, 3.6 |
| ревизия, хэш | ревизия растёт при каждой правке; хэш — SHA-256 канонической сериализации общих условий и хэшей общих вложений, добавленных до заключения |

### 3.2 Внутренние данные стороны (видит только она, в подпись не входят)

Внутренний номер, ответственный (контрактный менеджер), заметки, внутренние вложения, раздача полученных прав группам, напоминания. Хранятся по ключу `(contractId, tenantId)`, поэтому их правка не меняет ревизию и не сбрасывает подписи.

### 3.3 Сторона и её состояние

`ContractParty`: организация, роль в контракте (id + снимок названия), состояние, подпись, флаги.

| Состояние | Смысл | Переход |
|---|---|---|
| `INVITED` | в черновике, не отправлено | Submit → `REVIEWING` |
| `REVIEWING` | получила, рассматривает | RequestChanges / Approve / Sign / Decline |
| `CHANGES_REQUESTED` | просит изменить условия (комментарий; можно предложить новую сторону) | правка инициатора → `REVIEWING` |
| `APPROVED` | согласовано внутри стороны (юрист, руководитель); шаг необязателен | Sign / Decline |
| `SIGNED` | пользователь с правом подписи подписал эту ревизию | — |
| `DECLINED` | отказ (комментарий) | инициатор убирает сторону или отменяет контракт |
| `NOTICE_GIVEN` | подано уведомление о выходе, есть дата | дата → `WITHDRAWN`; отзыв → `SIGNED` |
| `WITHDRAWN` | вышла | — |

- **Подпись привязана к ревизии и хэшу.** Правка общих условий сбрасывает `APPROVED` и `SIGNED` всех сторон в `REVIEWING`. Каждый переход принимает ожидаемую ревизию; устаревшая — отказ.
- **Одна подпись на сторону.** `ContractSignature`: пользователь, снимок ФИО и должности, время, ревизия, хэш. Подписывает в системе любой пользователь стороны с правом `Contracts/Sign`; стороны подписывают параллельно.
- Инициатор после Submit проходит те же состояния — его подпись тоже нужна.

### 3.4 Общее состояние контракта

Вычисляется чистой функцией `ComputeContractState(contract, parties, now)`. Хранятся только факты: состояния сторон, `submittedAt`, `cancelledAt`, `terminatedAt` + причина, `supersededBy`. Для списков вычисленное значение кешируется в колонке при каждом переходе, временные состояния список досчитывает по датам.

| # | Условие (первое подошедшее) | Состояние |
|---|---|---|
| 1 | активирован заменяющий (`supersededBy`) | `SUPERSEDED` |
| 2 | `terminatedAt` наступил | `TERMINATED` |
| 3 | `cancelledAt` задан | `CANCELLED` |
| 4 | не отправлен | `DRAFT` |
| 5 | не все подписали, есть `DECLINED` | `REJECTED` |
| 6 | не все подписали, есть `SIGNED` | `SIGNING` |
| 7 | не все подписали | `NEGOTIATION` (подсостояние: есть `CHANGES_REQUESTED`) |
| 8 | все подписали, `now < effectiveFrom` | `SIGNED` (вступит в силу) |
| 9 | все подписали, период закончился без продления | `EXPIRED` |
| 10 | иначе | `ACTIVE` |

Срока оферты нет: неподписанный контракт инициатор отзывает сам (`CANCELLED`).

Признаки поверх `ACTIVE`: `TERMINATING` (есть `NOTICE_GIVEN` или назначено расторжение, с датой), `EXPIRING` (до конца периода меньше `renewalNoticePeriod` или 30 дней), `PARTIALLY_SUSPENDED`.

**Действует** = `ACTIVE`. Связи, права, обмен — только у действующего.

Продление вычисляется: при `autoRenew` конец периода — первая граница `effectiveFrom + term + k·renewalPeriod` после `now`. Уведомление о непродлении в момент `t` заканчивает контракт на первой границе `≥ t + renewalNoticePeriod`. Фоновое задание не нужно.

### 3.5 Ссылки на другие контракты

| Тип | Смысл |
|---|---|
| `SUPERSEDES` | полная замена: продление на новых условиях, допсоглашение, присоединение или исключение стороны. При активации нового старый получает `supersededBy` в той же транзакции; гранты и связи переходят без разрыва доступа |
| `FRAMEWORK` | дочерний договор рамочного. Стороны дочернего ⊆ сторон рамочного, срок внутри срока рамочного; рамочный не действует — дочерний тоже; распределения не шире рамочных для той же пары |
| `RELATED` | справочно |

Граф ацикличен. Ссылаться можно только на контракты, где инициатор — сторона. Действующий контракт неизменяем — только замена через `SUPERSEDES`.

### 3.6 Вложения

`ContractAttachment`: id, имя, MIME, размер, SHA-256, кто и когда добавил, видимость (`SHARED`/`INTERNAL`). Видов у вложений нет — это просто файлы.

- Общие файлы, добавленные до заключения, — часть условий: их добавляет только инициатор, их хэши входят в хэш контракта, новый файл или новая версия снова отправляет условия сторонам.
- После заключения любая сторона добавляет общие файлы (акты, сканы и т. п.); в условия они не входят. Подписанные файлы условий не заменяются.
- Общие вложения не удаляются, а заменяются новой версией.
- Данные — в `imtchat::IAttachmentStorage` (уже у `imtdesk`), подключается в `imtauthgql`; `imtauth` от `imtchat` не зависит.

### 3.7 Распределение прав

1. **Allocation — решение дарителя, на связи.** Сторона X сама отдаёт стороне Y, с которой у неё есть связь, набор **своих** прав в пространстве X, с необязательным сроком. Только права из области прав X, без передачи дальше, для дочернего контракта — не шире рамочного. Никто, кроме X, права X не распределяет: инициатор не вписывает чужие права.
   - Давать и забирать можно с черновика до окончания договора, кроме стороны, которая отказалась или вышла. Подписи и ревизия при этом не меняются, хэш условий распределений не включает.
   - Действуют права, пока действует договор и связь, в пределах срока распределения. Отдельной приостановки нет: даритель просто забирает распределение (`WithdrawContractPermissions`), получатель сразу теряет доступ и получает уведомление.
2. **Distribution — внутреннее решение Y.** Администратор Y выбирает свои группы. По умолчанию — никто; при активации администраторы Y получают уведомление.

Реализация через существующий путь доступа:

- При активации каждое распределение становится `CrossOrgGrant` с `contractId`, `linkId`, `allocationId`, набором прав и `targetGroupIds`. Грант принадлежит контракту, вручную не правится.
- `IDelegatedAccess` учитывает группы гранта. Гранты без контракта ведут себя как прежде.
- Эффективность = связь действует ∧ срок распределения.
- Расторжение, замена, выход, отзыв распределения меняют гранты в той же транзакции и публикуют событие изменения доступа. Окончание срока учитывается при каждой проверке, открытые подписки — через продление доступа.
- Серверы продуктов узнают о любом изменении контракта по подписке `OnContractsChanged` (её получают только серверы, в кадре id контракта и продукт) и сразу сбрасывают закэшированных пользователей: выданное и забранное действует на ближайшем запросе, без ожидания кэша. Подписка принимается только от сервера, предъявившего серверный токен (`IMT_PUMA_SERVER_CREDENTIAL`): заголовок продукта личность не доказывает. Сервер продукта без токена этой подписки не получает, и его кэш устаревает на время своей жизни (до 10 с).

### 3.8 Расторжение и выход

| Способ | Как | Итог |
|---|---|---|
| Истечение | вычисляется | `EXPIRED` |
| Непродление | уведомление до `renewalNoticePeriod` | `EXPIRED` на границе периода |
| Выход стороны | `NOTICE_GIVEN` с датой `now + terminationNoticePeriod`, затем `WITHDRAWN`; связи этой стороны заканчиваются | контракт живёт, если осталось ≥ 2 сторон, хотя бы одна связь и слоты типа заполнены; иначе `TERMINATED` |
| По нарушению | немедленный выход с причиной; свои распределения можно сразу забрать | как выход |
| Отмена оферты | инициатор до активации | `CANCELLED` |

### 3.9 Журнал и уведомления

- `ContractEvent`, только добавление: кто, от какой стороны, когда, что, ревизия. События внутренних данных видит только своя сторона.
- Уведомления (`NotificationType` в `.acc`): приглашение, запрошены изменения, подписан стороной, подписан всеми, вступил в силу, отклонён, уведомление о выходе, получены права, права забраны.
- Напоминания: истекает, последний день уведомления о непродлении.

## 4. Как организации находят друг друга

Организации по умолчанию **не видны** другим организациям. Найти организацию можно тремя способами, приглашать — четырьмя.

### 4.1 Каналы

| Канал | Как работает | Кого даёт |
|---|---|---|
| **Код подключения** (есть) | организация передаёт код вне системы; его можно перевыпустить или отключить | любую организацию, давшую код |
| **Адресная книга** (Connection, есть) | организации, с которыми уже есть подключение; появляется после одобренного запроса или автоматически после подписания контракта | контрагентов |
| **Участники общего контракта** | стороны рамочного или любого действующего контракта видят друг друга и могут приглашать друг друга в новые контракты без кода | участников общих сделок |
| **Каталог организаций** (новое, по желанию организации) | организация публикует профиль: название, описание, роли, в которых готова выступать, отрасль, страна; поиск по каталогу, из карточки — запрос на подключение | открытые для предложений организации |

### 4.2 Как собирается N-сторонний контракт

1. Инициатор добавляет стороны:
   - из адресной книги;
   - из участников общих контрактов (обязательно для дочерних рамочного);
   - по коду подключения — для незнакомой организации;
   - из каталога.
2. Задаёт роли, связи, условия; Submit.
3. Каждая сторона получает приглашение во входящие. Для стороны, приглашённой по коду или из каталога, это одновременно запрос на подключение к инициатору.
4. До Submit стороны не видят ничего. После — видят контракт целиком, включая других участников и их публичные профили, даже если с ними не подключены: подписывая, сторона соглашается и на связи с ними.
5. Сторона может в запросе изменений **предложить новую сторону** (по коду или из своей адресной книги); добавляет её инициатор.
6. После подписания для каждой пары связи появляется Connection, если его не было: стороны теперь в адресной книге друг друга. Удалить Connection можно, контракт и связи от этого не меняются.

### 4.3 Защита от злоупотреблений

- Приглашение по коду требует права `Connections/Edit/Connect`; код можно отключить, тогда организацию приглашают только знакомые.
- Организация может запретить приглашения в контракты от организаций вне адресной книги (по умолчанию разрешено для кода и каталога).
- Ограничение частоты приглашений от одной организации.
- Отклонённое приглашение по коду не создаёт подключения; повторное приглашение того же контракта отклонившей стороне невозможно — только новый контракт.
- Личное пространство (пользователь вне организаций) стороной контракта быть не может.

## 5. Справочники

### 5.1 Роли сторон

`IPartyRoleInfo`: стабильный ASCII `roleId`, название, описание, владелец (пусто = системная), парная роль (поставщик ↔ заказчик; партнёр ↔ партнёр), шаблон прав, признак архива.

- Системные роли — элементы `.acc` с переводами (как `NotificationType`): Parent, Child, Partner, Supplier, Customer, Affiliate (значения нынешнего enum, для переноса), Contractor, Subcontractor, Distributor, Agent, ServiceProvider, Licensor, Licensee, Guarantor.
- Собственные роли создаёт организация (`PartyRoles/Edit`), коллекция `PartyRoles`. Контрагенты видят роль в контрактах, где она использована.
- В контракте хранятся id и снимок названия. Используемая роль не удаляется, а архивируется.
- Роль используется дважды: роль стороны в контракте и направленная роль на связи.

### 5.2 Типы контрактов

`IContractTypeInfo`, системные и собственные: название, префикс номера, слоты ролей (`roleId`, `min`, `max`), схема связей по умолчанию (звезда вокруг роли / полная сетка / вручную), значения по умолчанию (срок, продление, уведомления), шаблон распределений по связям ролей.

Системные типы: **«Сотрудничество»** (замена Relationship: 2 стороны, одна связь, без вложений), «Поставка», «Оказание услуг», «NDA», «Рамочный».

### 6.1 Интерфейсы (`imtauth`)

### 6.2 Перенос существующих данных

Relationship в базах есть, и на них держатся расшарки — переносим, а не бросаем:

| Было | Стало |
|---|---|
| `TenantRelationships` (активная/в сроке/архив) | контракт типа «Сотрудничество», обе стороны `SIGNED` способом `MIGRATED`, одна связь с ролями из enum, тот же срок и описание, `effectiveFrom` = `CreatedAt`; архивная → `TERMINATED` с `UpdatedAt` (нужно для `relatedSince`) |

| `relationshipId` в сообщениях и заявках | `contractId`/`linkId` перенесённого контракта |

Перенос — миграция схемы, один раз; кода совместимости со старыми таблицами не остаётся.

## 8. Этапы

1. **Справочник ролей и типы** (системные `.acc` + собственные), GQL, права.
2. **Контракт:** модель, стороны и связи, `ComputeContractState` (табличный тест всех строк 3.4 и продления), подписи по ревизии/хэшу, ссылки, вложения, внутренние данные, журнал, уведомления.
3. **Замена Relationship:** `CContractRelationshipProviderComp`, брокер по `contractId`/`linkId`, расшарки по связям, запрос на подключение с контрактом «Сотрудничество», миграция 6.2, удаление Relationship/Proposal. Postman: расшарки и сообщения работают как раньше на перенесённых данных, `relatedSince` не изменился.
4. **Права:** гранты контракта, группы, события доступа. Postman: доступ появляется при активации и раздаче, исчезает при отзыве распределения, выходе, истечении, исключении из группы, не разрывается при `SUPERSEDES`.
5. **Поиск друг друга:** приглашение по коду в контракт, участники общих контрактов, автоматический Connection, каталог, настройки приглашений, ограничение частоты.
6. **QML:** адресная книга и каталог, список контрактов с фильтром по состоянию, карточка (стороны, связи, подписание, ссылки, вложения, распределения, журнал), внутренняя вкладка, раздача групп, справочники; экраны Relationship заменяются.

## 9. Принятые решения

1. Самостоятельной Relationship нет; связь — часть контракта, двусторонняя «связь» — контракт типа «Сотрудничество».
2. Connection остаётся только адресной книгой и каналом приглашений, доступа не даёт.
3. Распределение — набор своих прав, который сторона сама даёт и забирает; в подпись не входит.
4. До раздачи по группам права не получает никто.
5. Выход стороны — с уведомлением (немедленно — по нарушению); контракт живёт, пока ≥ 2 сторон, есть связь и слоты типа заполнены. Отдельного расторжения по соглашению нет. Грантор всегда может сразу забрать свои распределения. Договор «заканчивается» (`TERMINATING`), только если после ухода стороны оставшиеся его не держат.
6. Все стороны видят весь общий текст; двусторонние тайны — дочерним контрактом.
7. Стороны без Connection видят друг друга с момента получения контракта; после подписания пары связей попадают в адресные книги друг друга.

## 10. Вне объёма

Обязательства и вехи; подпись сканом и внешней ЭЦП; несколько подписантов от стороны и очерёдность подписания; срок оферты; расторжение по соглашению; платёжные условия сверх суммы; шаблоны текста договора с подстановкой полей.
